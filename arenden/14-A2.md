# A2 – Varför blev ringlistan sämre?
Etikett: analysera

Om incidenten händer igen vill vi kunna svara på en minut: vilken commit, vilken data och
vilka mätvärden låg bakom ringlistan?

**Uppgift:** återskapa incidenten i en pull request (se ärende 5). Visa sedan, bara med det
som finns i GitHub Actions:
1. Vilken commit modellen tränades från.
2. Vilken data den tränades på (kontrollsumman i `matvarden.json`).
3. Vilka mätvärden den hade, och vilket steg som stoppade den.

Skriv också vad som fortfarande inte går att spåra, och hur det skulle kunna lösas.

**Klart när:**
- [x] Svaren står här, med länkar till körningarna.

## Svar

Jag återskapade incidenten i PR #56 genom att höja tröskeln till 0,95 med `MIN_ROC_AUC`, på samma sätt som i ärende 5. Körningen blev röd: #56.

Allt nedan hittade jag direkt på körningens Summary-sida, utan att ladda ner något.

**1.**
Modellen tränades från `60b115150fa1a513dcca4fc26ba9da7ac7621ca2`. SHA:n står i rubriken på Summary, i artefaktens namn och i tabellen.

**2.**
`kundbas.csv`, med kontrollsumman `51df885d...c481bb`. Den är identisk med körning #50, så datan var densamma. Det var inte den som orsakade problemet.

**3.**
ROC AUC landade på 0,789 och accuracy på 0,824. Det var `python -m churn.evaluate` i jobbet `utvardera` som stoppade modellen, eftersom 0,789 är under 0,95. Därefter blev `ci-klar` röd så att PR:en inte går att merga, och `ringlista` kördes aldrig. Den dåliga modellen kom alltså aldrig fram till kundtjänst.

## Det som fortfarande inte går att spåra

- **Commiten är lite lurig på PR:er.** På en pull request är `GITHUB_SHA` en tillfällig merge-commit som inte finns i grenens historik, så den går inte att hitta med `git log`. Det skulle lösas genom att också skriva ut grenens riktiga commit (`github.event.pull_request.head.sha`) i Summary.
- **Man ser inte vilken tröskel som användes.** Man ser att modellen stoppades men inte mot vilken gräns. Enkelt fixat genom att lägga till tröskeln i `matvarden.json`.
- **Paketversionerna sparas inte.** Om scikit-learn uppdateras kan samma kod ge en annan modell. En låsfil, eller `pip freeze` sparad som artefakt, skulle lösa det.
- **Kontrollsumman säger bara *att* datan har ändrats, inte *hur*.** Den gamla datan går inte att få tillbaka. Det skulle kräva att datan versioneras, till exempel med DVC.
- **Allt försvinner efter 90 dagar.** Artefakter och loggar raderas som standard. För att kunna svara på en incident som är äldre än så borde modellerna sparas i ett modellregister, till exempel MLflow.
